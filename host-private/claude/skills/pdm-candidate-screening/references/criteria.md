# PdM 評価観点

実際の選考で使いながら、観点の定義・シグナル・質問を直していく。

## 想定している領域

規制のある業界の現場に、端末・周辺機器とソフトウェアを導入して運用するプロダクトである。
扱う範囲は、ローカルで動くアプリケーション基盤、Windows アプリケーション、現場への導入・設置、機器選定まで及ぶ。
国のガイドラインなどの制約を理解し、プロダクトの要件に落とし込む仕事が常にある。

そのため、Web 上で完結する SaaS だけを作ってきた人は、一緒に働くうえで苦労しやすい。
ソフトとハードが行き交う境界で何が起きるか、どんな工夫が要るかを理解できることが前提になる。

一方で、チームには個別の具体的な話から入る人が多い。
物事を抽象的に捉え、進め方・枠組み・伝え方を整理できる人も、別の型として求めている。

## 2 つの型

| 型       | 求める役割                                                           | 中心となる観点 |
| -------- | -------------------------------------------------------------------- | -------------- |
| 境界型   | ソフトと現場の物理的な制約の境界を理解し、要件とデリバリーを設計する | A1〜A4         |
| 枠組み型 | 抽象的に状況を捉え、進め方・枠組み・伝え方を整理する                 | B1〜B4         |

どの候補者も A・B・C すべての観点で評価し、どちらの型に寄っているかを判定する。
片方の型が強ければ、もう片方が弱いことは見送りの理由にしない。
ただし枠組み型でも B4（具体への降り方）が弱い場合は、チームと噛み合わないおそれが高いので懸念点に挙げる。

## 評価の目盛り

| 評価 | 意味                                           |
| ---- | ---------------------------------------------- |
| ◎    | 想定レベルを明確に上回る具体的な記述がある     |

## A. 境界型の観点

### A1. ソフトとハードの境界の理解

定義: OS・ドライバ・周辺機器・ネットワーク・電源など、ソフトの外側にある要素がプロダクトの振る舞いにどう影響するかを理解しているか。

- 良いシグナル: 端末やネットワークに起因する障害、オフライン動作、端末の個体差、OS 更新への追従などを扱った記述がある
- 弱いシグナル: クラウド上で完結するサービスの記述だけで、端末や現場の環境に触れていない
- 最初の問い:「ソフトの外側（端末・ネットワーク・周辺機器など）が原因の障害を経験したことはありますか」
- 深掘り:「原因はどうやって突き止めましたか。その後、仕様や運用で何を変えましたか」
- 良い回答の兆候: ソフト側で吸収すべきことと、運用や機器側で手当てすべきことを分けて考えている

### A2. 物理的なデリバリーの設計

定義: 現場への導入・設置・初期設定・保守・機器交換まで含めて、プロダクトをどう届けるかを設計できるか。

- 良いシグナル: 多拠点への展開、現地作業、キッティング、段階的な切り替え、導入後のサポート体制などの記述がある
- 弱いシグナル:「リリース」がデプロイで終わっていて、利用者の手元に届くまでの工程が出てこない
- 最初の問い:「数百の拠点に新しい端末とアプリを入れるとしたら、何を決める必要がありますか」
- 深掘り:「設置当日に、現地のネットワークがつながらなかったらどうしますか」
- 良い回答の兆候: 調達のリードタイム、現地作業の人員、切り戻し、現場の業務を止めない段取りまで話が及ぶ

### A3. 規制・ガイドラインの要件化

定義: 国のガイドラインや法令など外部の制約を読み解き、プロダクトの要件と運用に落とし込めるか。

- 良いシグナル: 法令・業界ガイドライン・認証制度・監査への対応を、要件定義や仕様に反映した記述がある
- 弱いシグナル:「セキュリティ対応」「コンプライアンス遵守」とだけ書かれていて、何を要件にしたかが分からない
- 最初の問い:「ガイドラインや法令の文言を、プロダクトの要件にしたことはありますか」
- 深掘り:「解釈が分かれたとき、どう決めましたか。システムで担保した部分と、運用で担保した部分はどこですか」
- 良い回答の兆候: 原文に戻って解釈を確かめている。責任の分担（自社・顧客・委託先）を意識している

### A4. 物理的な制約の中での判断

定義: 機器選定や現場の運用など、やり直しのコストが大きい判断を、制約を踏まえて下せるか。

- 良いシグナル: 機器やベンダーの選定、ハードウェアの制約を前提にした仕様の判断などの記述がある
- 弱いシグナル: 判断の記述がソフトウェアの機能の取捨選択だけ
- 最初の問い:「機器やベンダーを選定したことはありますか。何を比較の軸にしましたか」
- 深掘り:「選んだあとで困ったことはありましたか。次に選ぶなら軸をどう変えますか」
- 良い回答の兆候: 価格や性能だけでなく、調達の安定性・サポート期限・OS 対応・現場での扱いやすさを比べている

## B. 枠組み型の観点

### B1. 構造化・抽象化

定義: 個別の事象や混乱した議論から、論点と全体像を取り出して整理できるか。

- 良いシグナル: 混乱していたプロジェクトや議論を整理し、その結果として何が進んだかが書かれている
- 弱いシグナル: フレームワーク名の列挙だけで、整理した対象と結果がない
- 最初の問い:「議論が混乱していたプロジェクトを整理した経験を教えてください」
- 深掘り:「整理する前と後で、何が変わりましたか」
- 良い回答の兆候: 整理によって意思決定が速くなった、関係者の認識がそろった、など具体的な変化を語れる

### B2. 進め方の設計

定義: 関係者の多い取り組みで、フェーズ・会議体・判断の場などの進め方を設計できるか。

- 良いシグナル: プロジェクトの立ち上げや再設計で、進め方そのものを作った記述がある
- 弱いシグナル: 決められた進め方の中で担当した作業だけが書かれている
- 最初の問い:「関係者の多いプロジェクトで、進め方をどう組み立てましたか」
- 深掘り:「その進め方で、うまく回らなかった部分はどこですか。どう直しましたか」
- 良い回答の兆候: 誰がいつ何を決めるかを先に決めている。進め方を途中で直した経験がある

### B3. 伝え方

定義: 相手の立場に合わせて、同じ内容を伝わる形に組み替えられるか。

- 良いシグナル: 経営向けの提案、現場向けの説明、社外向けの資料など、相手に応じた発信の記述がある
- 弱いシグナル: 資料作成の記述が「作成した」だけで、相手や目的が見えない
- 最初の問い:「いま担当しているプロダクトを、経営層向けに 3 分で説明してください」
- 深掘り:「同じ内容を現場の利用者に説明するとしたら、何を変えますか」
- 良い回答の兆候: 結論から話す。相手が判断に使う情報を選んでいる

### B4. 具体への降り方

定義: 抽象的な整理に留まらず、境界型の具体的な話を理解し、論点に組み込めるか。

- 良いシグナル: 現場や技術の具体的な事情を踏まえて枠組みを作った記述がある
- 弱いシグナル: 提言や戦略立案で終わっていて、実行や成果に関わった記述がない
- 最初の問い: 面談の中で A1 や A2 の具体的な事例（端末の障害や設置の失敗など）を一つ話し、「これを論点に整理するとどうなりますか」と聞く
- 深掘り:「整理するうえで、分からない技術的な要素はどこでしたか」
- 良い回答の兆候: 知らない要素を自分から質問する。具体の話を拾って構造にしている。一般的なフレームワークを当てはめるだけで終わらない

## C. PdM 共通の観点

- C1. 課題発見・顧客理解: 課題を見つけた手段と、そこから分かったことが書かれているか。問い「直近で、自分で見つけた課題を一つ教えてください」
- C2. 成果志向: リリースした機能ではなく、指標と変化量で仕事を測っているか。問い「その施策の成功を、どの指標で判断しましたか」
- C3. 優先順位付け: やらないと決めたことと、その基準を説明できるか。問い「最近、やらないと決めたことは何ですか」
- C4. 合意形成: 利害の違う関係者と、どう着地させたか。問い「強い要望を断ったか、形を変えた経験はありますか」
- C5. 振り返り・再現性: 失敗から何を変えたか。成果のうち自分の寄与と環境の追い風を分けて話せるか。問い「一番うまくいかなかったプロジェクトを教えてください」

## 書類の懸念点（レッドフラグ）

| 懸念点                               | 書類での見え方                                                   | 面談での確かめ方                                                                      |
| ------------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Web 上で完結する経験だけ             | クラウドの SaaS 開発の記述だけで、端末・現場・規制に触れていない | A1・A2 の質問。オンプレミス案件やモバイルのオフライン対応など、近い経験がないかも聞く |
| 抽象的な整理だけで実行がない         | 提言・戦略・フレームワークの記述が中心で、成果や実行の記述がない | B4 の質問                                                                             |
| 出力だけで成果がない                 | 機能リリースの列挙、数字が工数や件数だけ                         | C2 の質問                                                                             |
| 本人の寄与が不明                     | 主語が「チーム」「プロジェクト」だけ                             | 「その中であなたが決めたことは何ですか」                                              |
| PdM の肩書きでプロジェクト管理が中心 | 進行管理・ベンダー調整・WBS の記述が大半                         | A4・C3 の質問                                                                         |
| ツールや手法の名前だけ               | 手法名・ツール名の列挙のみ                                       | 「それを使って何を判断しましたか」                                                    |

Web 上で完結する経験だけでも、それだけで見送りにはしない。境界の話への関心と理解の速さを面談で確かめる。
在籍期間の短さやブランクも、それだけでは懸念点にしない。

## 面談で聞いてはいけないこと

厚労省「公正な採用選考の基本」で、就職差別につながるおそれがあるとされる事項は質問しない。
本籍・出生地、家族（職業・続柄・収入など）、住宅状況、生活環境・家庭環境、宗教、支持政党、人生観・生活信条、尊敬する人物、思想、労働組合・学生運動などの社会運動、購読新聞・愛読書などがこれにあたる。
