# 読み手の負荷の管理・語の一貫性・ページの範囲・冗長の排除・読者への誠実さ・既存文書のリライト

## 読み手の負荷の管理

読者の記憶と注意は有限の資源として扱う。

- 後で参照する必要のない固有名（ファイル名、関数名、識別子）を出さない。「仕様書」「金額計算のユーティリティ」のような一般的な言い方で済ませる。
- 抽象的な言い回しの指す内容が文脈から一意に決まらないときは、可能なときは丸括弧による同格挿入でその場で特定し、できるだけ読者に前を読み返させない。
- 指示語（「この出力」「その経路」）や限定の修飾語（「専用の」「独自の」）を、指す先を書かずに済ませない。何の出力か、何に対して専用かをその場で書く。分野の中で複数の対象を指しうるドメイン固有の名詞（「連携」「マスタ」「権限」など）も同じで、修飾なしで置かない。何の・どこの・誰のものかをその場で補うか、`用語` の表で定義する。ただし、表に足すだけでは読めるようにならない（次の2項目）。
- `用語` の表の項目には、定義（何か）だけでなく、その項目が何のためにあるかを書く。桁数や位置だけを書いても、読み手はその項目の存在理由がわからない。悪い例：「旧ファイル名＝更新前のファイル名」。良い例：「旧ファイル名＝処方箋番号が変わったとき、受取側が変更前の番号をたどるために置かれている項目」。
- 複数の語が1つの構造の部分を指しているなら、表の前に構造の全体像を1文で置く（「ファイル名は21桁で、更新区分1桁、処方箋番号15桁、予備5桁が並ぶ」）。個々の定義を読む前に、どこの話なのかがわかる。
- 語を表に足したぶん本文の説明を減らしてよい、とは考えない。表は参照用であり、本文を読み進めるための説明は本文に要る。
- 何のためにある項目かがもとの資料から読み取れないなら、目的を作らない。未確認であることを本文か確認事項の節に残し、書ける相手に確認する（「読者への誠実さ」）。悪い例：用途の記述がない「予備5桁」に「将来の項目追加のために空けてある領域」と書く。
- 他の文書の節・設問・課題を参照するときは、番号だけを置かない。番号にタイトルか内容の要約を添える。節を指すなら「材料 3-10」で止めず、「材料 3-10 設定の持ち場所」とタイトルまで書く。設問を指すなら、番号ではなく設問文を書き起こす。番号は書き手には通じるが、読み手には解けない。
- 参照した別ページの設問を自分の議論の前提として使うなら、番号とタイトルでも足りない。その設問が何を問うていたのかを本文に書き起こす。「材料の 3-6 が立てていた問い」と書いた側は中身を覚えているが、読み手は材料を開かないと読み進められない。
- 同じページの中でも、位置で指す参照で済ませない。「1つめと2つめの前提から導かれる」ではなく、その2つの前提の中身を書く。「前述のとおり」も同じで、何を前に述べたのかをその場に書く。読み手は番号を数えながら読まない。
- 参照した論点をそのページで扱わないなら、扱わないことを明示する。参照を置くだけでは、議論の省略なのか別ページへの委譲なのかを読み手が判断できない。
- 新しい例や場面を追加して、読者が保持すべき文脈が増えるときは、前の例と何が違うのか、なぜもう一つ必要なのかを前置きして納得感を与える。
- 章冒頭や節の導入では、これから例で扱う内容に関係しない過剰な詳細を詰め込まない。
- 例の節の中でも、**その節の問い・帰結に関係しない**過剰な詳細だけを omit する。議論に必要な具体は残す。省略の典型は、エージェント報告の装飾的精度（時刻、HTTP ステータス、カバレッジ率など）や、後で参照しない固有名

## 同じ語を1つの文書の中で2つの意味に使わない

多義語に修飾を足す規範とは別に、同じページの中で同じ語が別の意味を持つことを許さない。

- 意味が2つあるなら、修飾を足すのでは足りない。意味ごとに別の語を立てる。
- 同じ語が別のことを指していると、根拠と結論の両方に同じ語が現れる。読み手には循環した論証に見える。悪い例：「いったん出力した処方箋番号を修正保存しても変えない」ことと「採番規則が調剤日に依存しない」ことを、どちらも「固定」と呼ぶ。そのため「Noah V7 は既に番号固定で動いている」が、固定を根拠に固定を導く文に見えていた。
- 書き分けるときは、その意味をそのまま述べる語にする。上の例では、前者を「修正保存時も同じ処方箋番号を使う」、後者を「調剤日を含まない採番規則」に分けた。
- 分けたら、両者の関係も本文に書く。上の例なら「調剤日に依存しない採番規則だから、結果として修正保存しても値が変わらない」である。
- 推敲では、ページ内で繰り返し出てくる語を拾い、出現箇所ごとに何を指しているかを確かめる。2つの意味で使っていたら、どちらも書き分ける。

## 読み手と共有されていない語を作らない

書き手の頭の中にしかない短縮形を読み手に投げない。

- 語は新しく作らず、すでに通用しているものを使う。仕様書の用語、製品名、社内で定着した呼び方、元の文書が使っていた語をそのまま引き継ぐ。
- 見出しや表の項目名を短くしたいという理由で、内容を圧縮した略称を作らない。短さより、読み手がその場で意味を取れることを優先する。
- 略すと指す対象が広がる語を使わない。「クラウドレセコン」を「クラウド」と略すと、クラウド一般を指す語になる。長くなっても製品名・システム名で書く。
- 短い名詞句にできないなら、平易な疑問形や長めの句のままにしておく。参照した別ページの見出しが短い名詞句だからといって、形を合わせるために縮めない。
- どうしても新しい語が必要なら、`用語` の表か初出箇所で定義する（初出の定義は太字。formatting-and-headings.md を参照）。

## そのページに属さない内容を置かない

書いている最中に手元で必要だった情報は、読み手には要らないことが多い。

- ページの冒頭には、どこから切り出した話かと、そのページで扱う範囲だけを置く。そこに至った検討の経緯や、本文の節で述べる結論の先出しは置かない。結論は節の中にあれば足りる。
- 自分向けの作業メモを、読み物として読まれるページに置かない。「元の材料への反映」のような、親ドキュメントをこう直すという作業リストが典型である。別のファイルか課題管理側に出す。

## 冗長の排除

無駄な文章をなるべく残さない。

- 同じ主張を言い換えて繰り返さない。一つの主張は一度だけ書く。
- 隣接する節が同じことを別の角度で述べているなら、役割が重複している。片方に吸収して一つの節にまとめる。
- 場面を描写した直後に、その内容を要約し直さない。意味づけの一文（「このような作業は、ほぼ完全に任せられる」など）だけを置く。
- 同じ論理的役割を持つ並列の事実は、文を分けて重ねず一文にまとめる。その事実群の論理的地位は文頭の語で示す（「当然、経理部の月次処理も顧客の支払いも〜」）。
- 読者が自力で補える中間段階の説明は書かない。
- 数文にわたる議論を一文に圧縮できるなら、圧縮した一文だけを残す。要約の合図として「要するに」を使ってよい。
- 接続や評価のためだけの文（「それ自体はよいことである」など）を置かない。
- 想像上の読者との問答（問いを立てて一語で答える形など）を修辞として使わない。主張はそのまま述べる。読者の反応を演じて応答する形（「〜と感じたかもしれない。そのとおりである」）も同様に避け、譲歩は地の文で簡潔に行う（「もちろん、処置そのものは開発者が決める問題ではない」）。
- 読者が抱きそうな発想を、メタな枠取り（「ここまでの話には自然な続きがある」「〜という発想である」）で紹介しない。その発想自体を直接書く。読者の疑問なら疑問文のまま書いてよい（「その保守も任せればよいのではないだろうか」）。
- 「本書もそれを否定しない」のような、著者の立場の弁明や断りを書かない。事実の記述（「〜に書かせる場合が多い」）だけを置く。
- 文脈を最短で読み手と共有できる文章にする。導出を一歩ずつ展開しなくても伝わるなら、構造に名前を与えて言い切る。
- 本文でまだ導入していない概念や文書名を、先回りして持ち出さない。
- ためらいのある弱い述語（「有効な対策であり」など）で済ませない。本文内の根拠で確定していることは強く具体的に言い切る（「活用において必須であり」など）。ただし、不確実性・可能性・仮定・読者の疑念を表すための弱い述語は保持する。語調を整えるための意図的な緩和（「必須だと言ってもいい」など）は許す。
- 文章のリズムを作るための接続表現（「しかし一方で」など）は、冗長と見なさない。

## 読者への誠実さ

- 例が作為的に見えると読み手が感じうる場合に限り、その疑念に短く触れる。誰も気にしない例に弁明を足さない。
- 触れるときの根拠は、著者の断定（「十分あり得る状況だ」）ではなく、読み手自身の経験に訴える一般的事実や通説に求める（「この症状は珍しくないだろう」「〜という言い方もよく耳にする」）。
- 確認していないことを、確認したかのように滑らかに書かない。

## 既存文書のリライト

リライトは文の形を変える作業だが、誤った事実に形を与えると誤りが強まる。

- 書き始める前に、もとにする版が最新かを確かめる。同じ文書のより新しい草稿が、ローカルの作業ファイルや git 履歴に残っていないかを見る。古い版から書き換えると、書き換えた分がまるごと無駄になる。
- 体裁だけを整えるつもりでも、引き継ぐ事実の主張（課題キー、URL、日付、数値、他システムの状態）は出典に当てて確かめる。元の草稿にあったからといって、確かめずに整形して通さない。
- 確かめられなかったものは、確認済みのような書き方に整えない。未確認であることを本文に残すか、確認事項の節へ降ろす。
