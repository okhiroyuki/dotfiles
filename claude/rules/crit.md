## crit レビュー

- crit をどの質問の選択肢に出すかは review.md が定める。このファイルは crit を起動したあとの注意だけを扱う
- 以下の挙動・原因・対処手順は出典が未確認である(根拠は要確認)
- `crit` に渡す差分のファイル名は ASCII にする。 `crit` は日本語名のファイルを表示せず、エラーも出さない
- 症状はサマリの件数が変更ファイル数より少なくなることだけである。そのまま承認すると、表示されなかったファイルを見ないまま通すことになる
- `core.quotepath` を無効にしても直らない。環境変数で渡すと `git diff --name-only` の出力は素の UTF-8 になるが、 `crit` 側の表示は変わらない。原因は git のパス表示ではなく `crit` 内部にある
- 既に日本語名で作ってしまった場合は、ベースのコミットごと ASCII 名で組み直し、差分を修正のみに保つ
- レビュー後はサマリの件数と `git diff --name-only | wc -l` を比べる。合わなければ不完全なレビューなので、名前を直して再度回す

## レビュー後の記録とスキルへの反映

- crit に指摘がある場合は、指摘内容を llm-wiki の crit 知見ページに追記する。指摘がない場合は追記しない
- crit 知見ページのタイトルは「crit の指摘と対策」、slug は crit-findings とする
- llm-wiki search で crit 知見ページを探し、なければ `concept` カテゴリで作る(1 ページを継続更新)
- 追記は日付、対象、指摘の要旨、対応の順に短く書く。指摘の要旨が同じ規律・同じ原因を指すときは同じ内容とみなし、同じ項目に新しい日付を足す
- 指摘が文章規律として一般化できるときは、crit 知見ページにスキル反映候補として記録する。crit の完了時にスキルへの反映を質問しない
- スキルの改善は、反映候補がたまったときや改善を依頼されたときに提案し、ユーザーの確認を取ってから行う
- 反映先は、表現と文体の規律なら japanese-tech-writing に、文書の情報構造の規律なら cognitive-load-docs に振り分ける
- 反映は skill-management スキルの手順に従い、評価の要否も改善の実行時に判断する
